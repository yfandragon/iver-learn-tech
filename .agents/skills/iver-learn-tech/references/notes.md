# 写给学习者看的笔记

新学习默认在学习目录维护 `notes.md`；沿用已有可读笔记，不因目录格式变化重写整套内容。笔记负责恢复理解与运用，能力证据和任务状态放在进度记录中。

## 先速览，再把原因讲清楚

开头给简短关键点速览，方便遗忘后迅速找回判断。正文围绕问题、场景和因果关系自然展开，保留足以重新理解的例子与边界。

根据主题需要讲清：问题为什么出现、机制怎样起作用、例子里发生了什么、疑问如何解决、什么条件下需要换一种判断。用完整连贯的解释，不把正文压成只有术语的清单。

应用方向按需附操作要点、实验或作品入口；面试方向按需附概括表达、方案权衡和追问。学习者先理解因果，再压缩表达，不默认背诵标准答案。每个主题只写必要部分，不机械填满相同栏目。

例如，下面是一个假设场景的写法，不代表学习者实际犯过这个错误：

> **为什么设置了过期时间，更新后还是可能读到旧值？**
>
> 假设接口先读缓存。缓存里是 100，数据库改成了 120，但更新流程没有处理缓存，那么再次读取仍可能得到 100。过期时间限制的是缓存的有效期，并没有替你同步两个存储。排查这个场景时，要沿更新和读取流程找原因。

真实项目的解释应结合实际代码和资料核对，不能将假设例子升级为所有实现的结论。

## 持续整理问题与纠错

- 每完成一个小主题或纠正关键误解，增量更新相关段落；结束时归并重复解释并更新速览、导航。
- 将实际疑问与纠错融入对应主题，保留有助于理解的原因，不转录冗长聊天。不虚构“你最初以为”或“你曾经做过”。
- 发现笔记有误时修正当前结论，必要时简短说明旧误解与修正依据；不要让互相矛盾的说法同时作为答案存在。
- 区分实际经历、假设场景和有依据的常见误解。未解决的问题标为待核对，不编造答案。
- 需要学习者先预测或作答的练习，先等待其尝试，再整理答案和纠错。当前练习尚未完成时，只记录开放问题或已经讲解的内容。
- 新发现的扩展主题先留在后续路线中，不因写笔记自动扩大学习计划。

## 资料与实验的写法

在影响关键判断的地方保留必要的一手来源和版本信息。说明资料确认了什么、实验在什么条件下观察到了什么，以及还有什么未验证；不要求每个段落附长串引用。

操作或代码写出可找到的入口、必要前提和已观察结果。未实际运行时注明示例或待验证，不虚构输出。若实验只覆盖正常场景，结论不要扩成并发、故障或全部环境下的保证。

## 可灵活使用的骨架

```markdown
# 技术主题：学习笔记

## 关键点速览

简短恢复核心判断，并指向详细主题。

## 围绕当前问题的主题标题

从具体问题或场景讲起，连贯解释机制与因果，配必要例子，说明适用边界；融入实际疑问和纠错。

按需要附实验／作品入口，或面试概括与追问。

## 待核对的问题

仅保留尚未解决、确实影响本轮理解的问题；没有时省略。

## 参考资料

仅列相关来源与必要版本信息，可直接放在对应正文附近。
```

回看后用一个小任务或追问检查能否重新应用。读过笔记本身不升级能力状态；需要时回到对应段落补理解，再针对薄弱点练习。
